# 코드 리팩토링 가이드

## 1. 리팩토링의 목적

이 작업의 목적은 **기존 기능과 동작을 유지하면서 코드의 가독성, 유지보수성, 확장성을 개선하는 것**이다.

단순히 코드를 짧게 만들거나 새로운 디자인 패턴을 적용하는 것이 목적이 아니다.

우선순위는 다음과 같다.

1. 기존 동작 유지
2. 코드의 의도와 책임 명확화
3. 불필요한 복잡성 제거
4. 중복 제거
5. 유지보수성 향상
6. 향후 기능 변경에 유리한 구조

---

## 2. 가장 중요한 원칙

### 기존 동작을 임의로 변경하지 않는다

리팩토링 과정에서 다음을 임의로 변경하지 않는다.

- 비즈니스 로직
- 함수의 결과값
- API 동작
- DB 처리 방식
- 에러 처리 방식
- 예외 발생 조건
- 외부 인터페이스
- 파일/데이터 형식
- 로그의 의미
- 기존 설정값
- 성능 특성

기존 코드가 이상해 보이더라도 **명확한 근거 없이 기능 변경으로 판단하지 않는다.**

기능 변경이 필요하다고 판단되면 리팩토링과 분리하고, 변경이 필요한 이유를 먼저 설명한다.

---

# 3. 리팩토링 전 분석

코드를 수정하기 전에 먼저 전체적인 구조와 동작을 파악한다.

다음 항목을 확인한다.

### 3.1 호출 관계

- 해당 함수가 어디에서 호출되는가?
- 해당 함수가 어떤 함수를 호출하는가?
- 호출하는 쪽에서 반환값이나 부작용에 의존하고 있는가?

### 3.2 데이터 흐름

```text
입력
 ↓
검증
 ↓
처리
 ↓
변환
 ↓
출력
```

데이터가 어떤 과정을 거쳐 변경되는지 파악한다.

### 3.3 외부 의존성

다음과 같은 외부 의존성이 있는지 확인한다.

- DB
- 파일
- 네트워크
- 외부 API
- 환경 변수
- 전역 변수
- 설정 파일
- 외부 라이브러리

### 3.4 부작용

함수가 단순히 값을 반환하는 것처럼 보여도 실제로 다음과 같은 작업을 수행하는지 확인한다.

- 전역 상태 변경
- DB 변경
- 파일 생성/수정
- 로그 출력
- 메모리 할당/해제
- 외부 API 호출
- 다른 객체의 상태 변경

---

# 4. 리팩토링 대상 판단 기준

다음과 같은 코드를 우선적으로 검토한다.

## 4.1 지나치게 긴 함수

하나의 함수가 여러 책임을 가지고 있다면 분리를 검토한다.

예:

```text
process()
 ├─ 입력 검증
 ├─ DB 조회
 ├─ 데이터 변환
 ├─ 비즈니스 로직
 ├─ 파일 저장
 └─ 로그 출력
```

다만 단순히 함수의 줄 수만 보고 분리하지 않는다.

**하나의 논리적 책임을 가지고 있다면 코드가 길더라도 억지로 분리하지 않는다.**

---

## 4.2 중복 코드

동일하거나 매우 유사한 로직이 반복되는지 확인한다.

단, 단순히 코드가 비슷하다는 이유만으로 공통 함수로 만들지 않는다.

현재는 비슷하더라도 **변경 이유가 서로 다르다면 분리된 상태를 유지한다.**

공통화했을 때 오히려 결합도가 증가하지 않는지 판단한다.

---

## 4.3 복잡한 조건문

다음과 같은 코드를 검토한다.

```text
if (A && B && !C && (D || E) && F)
```

조건의 의미를 명확하게 표현할 수 있다면 개선한다.

예:

```text
isValidUser
isAvailable
hasPermission
isRetryable
```

단, 단순한 조건까지 불필요하게 변수로 추출하지 않는다.

---

## 4.4 깊은 중첩

다음과 같이 중첩이 지나치게 깊은 코드는 개선을 검토한다.

```text
if
 └─ if
     └─ if
         └─ if
             └─ ...
```

가능한 경우 다음을 활용한다.

- Early return
- 함수 분리
- 조건식 단순화

단, Early return을 무조건 적용하지 말고 기존 코드의 흐름을 더 명확하게 만드는 경우에만 적용한다.

---

# 5. 네이밍 원칙

변수, 함수, 클래스, 모듈의 이름만 보고 **무엇을 의미하는지 추측할 수 있어야 한다.**

지양:

```text
data
tmp
flag
ret
process
handle
doWork
```

가능하면 의미를 명확하게 표현한다.

예:

```text
userData
temporaryFilePath
isInitialized
retryCount
validateUser
loadConfiguration
```

단, 프로젝트에서 이미 사용하는 네이밍 규칙이 있다면 **프로젝트의 기존 규칙을 우선한다.**

---

# 6. 함수 분리 원칙

함수를 분리할 때는 **기능 단위가 아니라 책임 단위**를 기준으로 판단한다.

좋은 예:

```text
loadUser()
validateUser()
calculatePrice()
saveOrder()
```

좋지 않은 예:

```text
doStep1()
doStep2()
doStep3()
```

함수 하나를 무조건 작은 함수 여러 개로 만드는 것을 피한다.

다음 조건을 만족하는 경우 함수 분리를 적극적으로 검토한다.

- 함수의 책임이 명확하게 분리되는 경우
- 동일한 로직을 재사용해야 하는 경우
- 테스트가 어려운 로직을 독립적으로 테스트할 필요가 있는 경우
- 복잡한 세부 구현을 상위 로직에서 숨길 수 있는 경우

---

# 7. 의존성

다음과 같은 구조를 주의한다.

- 불필요한 전역 변수
- 강한 모듈 간 결합
- 순환 의존성
- 지나치게 많은 함수 파라미터
- 특정 구현에 직접적으로 의존하는 코드
- 하나의 변경이 여러 모듈에 연쇄적으로 영향을 주는 구조

리팩토링의 목표는 가능한 경우:

```text
낮은 결합도
+
높은 응집도
```

를 만드는 것이다.

---

# 8. 에러 처리

기존의 에러 처리 로직을 반드시 확인한다.

특히 다음을 확인한다.

- 반환값
- 예외
- 에러 코드
- 로그
- resource cleanup
- 메모리 해제
- DB rollback
- 파일 close
- connection release

리팩토링 과정에서 정상적인 흐름만 개선하고 **에러 흐름을 누락시키지 않는다.**

---

# 9. 성능

리팩토링 과정에서 불필요한 성능 저하가 발생하지 않는지 확인한다.

특히 다음을 확인한다.

- 불필요한 반복 연산
- 불필요한 메모리 할당
- 불필요한 데이터 복사
- 불필요한 DB 호출
- 불필요한 파일 I/O
- 불필요한 네트워크 호출
- 불필요한 객체 생성

단, **측정되지 않은 성능 문제를 해결하기 위해 코드 구조를 지나치게 복잡하게 만들지 않는다.**

가독성과 유지보수성을 우선한다.

---

# 10. 과도한 리팩토링 금지

다음과 같은 작업은 명확한 필요성이 없다면 하지 않는다.

- 새로운 디자인 패턴 도입
- 불필요한 추상화
- 과도한 클래스 생성
- 지나치게 작은 함수 생성
- 단순한 코드를 복잡한 구조로 변경
- 사용하지 않는 범용 기능 추가
- 미래의 가능성을 고려한 과도한 설계
- 전체 프로젝트 구조의 대규모 변경

**현재 필요한 문제를 해결하는 범위에서 가장 단순한 구조를 선택한다.**

---

# 11. 기존 프로젝트 스타일 우선

프로젝트에 이미 존재하는 규칙을 최대한 따른다.

확인할 항목:

- 디렉터리 구조
- 파일 구조
- 네이밍
- 코딩 스타일
- 에러 처리 방식
- 로그 방식
- 함수 작성 방식
- 클래스/모듈 구성
- 사용하는 라이브러리
- 기존 디자인 패턴

새로운 스타일을 적용하기 위해 기존 프로젝트 전체의 스타일을 변경하지 않는다.

---

# 12. 리팩토링과 기능 변경을 분리

다음 두 작업을 구분한다.

### 리팩토링

```text
기존 기능
   ↓
동일한 기능
+
더 나은 코드 구조
```

### 기능 변경

```text
기존 기능
   ↓
새로운 기능 / 변경된 동작
```

두 작업을 동시에 수행해야 한다면 반드시 **어떤 부분이 리팩토링이고 어떤 부분이 기능 변경인지 구분해서 설명한다.**

---

# 13. 변경 범위

가능하면 한 번에 작은 범위만 변경한다.

권장 순서:

```text
코드 분석
 ↓
리팩토링 대상 선정
 ↓
작은 단위 변경
 ↓
빌드
 ↓
테스트
 ↓
동작 확인
 ↓
다음 변경
```

한 번에 프로젝트 전체를 대규모로 변경하지 않는다.

---

# 14. 테스트

리팩토링 후에는 가능한 범위에서 다음을 확인한다.

### 컴파일 / 빌드

- 컴파일 오류가 없는가?
- warning이 새롭게 발생하지 않는가?
- 빌드가 정상적으로 완료되는가?

### 테스트

- 기존 테스트가 통과하는가?
- 주요 기능이 정상 동작하는가?
- 예외 상황도 기존과 동일하게 동작하는가?

### 정적 분석

프로젝트에서 사용하는 정적 분석 도구가 있다면 함께 확인한다.

---

# 15. 리팩토링 결과 보고

리팩토링 후에는 다음 내용을 간단하게 정리한다.

```text
## 변경 내용

- 어떤 파일을 변경했는지
- 어떤 함수를 변경했는지
- 어떤 문제를 해결했는지
- 왜 해당 방식으로 변경했는지

## 동작 영향

- 기존 기능에 영향을 주는 변경이 있는지
- API 변경이 있는지
- DB 동작 변경이 있는지
- 기타 주의사항

## 검증

- 빌드 결과
- 테스트 결과
- 추가로 확인이 필요한 사항
```

---

# 16. 최종 판단 기준

리팩토링 결과를 다음 질문으로 평가한다.

```text
1. 기존 동작이 유지되는가?
2. 코드를 이해하기 쉬워졌는가?
3. 각 코드의 책임이 명확해졌는가?
4. 중복이 적절하게 제거되었는가?
5. 의존성이 불필요하게 증가하지 않았는가?
6. 에러 처리가 유지되는가?
7. 성능이 불필요하게 저하되지 않았는가?
8. 프로젝트의 기존 스타일과 일관되는가?
9. 테스트하기 쉬워졌는가?
10. 앞으로 변경하기 쉬워졌는가?
```

**위 기준을 만족하지 못하는 변경은 단순히 코드가 더 깔끔해 보인다는 이유만으로 적용하지 않는다.**

---

# Claude 작업 지침

코드를 리팩토링할 때는 **바로 수정부터 하지 말고 먼저 코드를 분석한다.**

1. 현재 코드의 역할과 구조를 파악한다.
2. 리팩토링이 필요한 부분을 식별한다.
3. 각 부분에서 발생하는 문제를 설명한다.
4. 변경으로 인해 발생할 수 있는 영향을 확인한다.
5. 가장 단순하고 안전한 리팩토링 방법을 선택한다.
6. 기존 동작을 최대한 유지하면서 수정한다.
7. 수정 후 빌드 및 테스트가 가능하면 수행한다.
8. 실제로 변경한 내용을 요약한다.

**코드를 더 짧게 만드는 것보다 이해하기 쉽고 변경하기 쉬운 코드를 만드는 것을 우선한다.**

**확신이 없는 부분은 임의로 변경하지 말고, 해당 부분을 리팩토링하지 않은 이유를 명시한다.**
